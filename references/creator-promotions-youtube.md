# YouTube creator promotion sources

The client in [`lib/creator-promotions/youtube.mjs`](../lib/creator-promotions/youtube.mjs) reads public channel video entries and the documented YouTube Data API v3. It returns titles, public channel IDs, video URLs, publication timestamps, and descriptions. Korean and English terms such as collaboration, co-development, coupon, discount, group-buy, sponsored disclosure, and affiliate reference are returned as **text hints** with character offsets. These hints describe the creator's text; they do not verify a promotion, a product match, a discount, or sponsorship.

## Sources and limits

| Operation | Source | Authentication | Coverage |
|---|---|---|---|
| `getChannelFeed({channelId})` | `GET https://www.youtube.com/feeds/videos.xml?channel_id=...`; official push-notification guide identifies this feed URL and Atom video/channel/title/link/published fields | No account or API key in the observed successful response | Recent entries for a known channel only; no keyword discovery. The feed also carried `media:group/media:description` in the observed sample, but descriptions are optional at the adapter boundary. |
| `getSearchPageVideos({query,maxItems})` | `GET https://www.youtube.com/results?search_query=...`; reads the current `ytInitialData` JSON assignment in the server-rendered search document | No account or API key in the observed successful response | One result page. Only `videoRenderer`s under `contents.twoColumnSearchResultsRenderer.primaryContents` are considered; video ID and same-origin watch link must agree. HTML field names are an observed page contract and can change. This is a public-document read, not XHR and not the Data API. |
| `getVideoPageMetadata({videoId})` | `GET https://www.youtube.com/watch?v=...`; bounded direct HTTP read of the page's current `ytInitialPlayerResponse` JSON bootstrap | No account or API key; Node's ordinary HTTP client | One requested public video at a time. The output is marked `first_party_public_document`, `isXhr:false`; this optional page parser is not presented as a documented API or an XHR capture. It never executes page scripts or follows description URLs. |
| `searchVideos({query,...})` | `GET https://www.googleapis.com/youtube/v3/search`, `part=snippet`, `type=video` | YouTube Data API key | One relevance/date-filtered result page. Search totals are approximate. The API key is placed in the request query but never returned in output, receipts, or errors. |
| `getVideos({videoIds})` | `GET https://www.googleapis.com/youtube/v3/videos`, `part=snippet`, IDs batched by 50 | YouTube Data API key | Public snippet fields for exact requested IDs; private/deleted/unavailable IDs are reported as missing. |
| `collectSearchVideos({...})` | Repeated documented `search.list` pages using `nextPageToken` | YouTube Data API key | Explicitly limited by page and item caps; `complete` remains false because search is relevance-limited and the reported total is approximate. |

Google's current `search.list` reference documents the query, result type, language/region, date bounds and continuation token. Its example uses a developer key. `videos.list(part=snippet)` exposes channel ID/title, title, description and publication time. See [Search: list](https://developers.google.com/youtube/v3/docs/search/list), [Videos: list](https://developers.google.com/youtube/v3/docs/videos/list) and [Subscribe to Push Notifications](https://developers.google.com/youtube/v3/guides/push_notifications).

The documented feed was replayed once with HTTP 200 and a description on the Google for Developers channel. Later direct requests to that same feed and to four beauty-creator channel feeds returned HTTP 404; those results are preserved in the verification record. Thus a successful current creator-feed read is not claimed. A normal Node HTTP read of the current public YouTube search page returned HTTP 200 and exposed `ytInitialData` with four matching `videoRenderer`s. The separately declared `getSearchPageVideos` method parsed that observed JSON and then `getVideoPageMetadata` read the four selected public watch pages to obtain descriptions and exact publication dates. The search and watch page sources are explicitly public-document metadata, not XHR and not the documented Data API contract.

The YouTube Data API keyless `search.list` and `videos.list` probes returned HTTP 403. No keyed live call is claimed. Configure the API key through the caller's process-memory secret provider before using keyword search or bulk detail lookup. Do not print the key or put it in a receipt.

## Promotion evidence model

Each result retains the source video description as requested public business data and a SHA-256 digest to identify the exact observed text. It also includes `promotionHints`, a list of exact matched terms with `field`, `startUtf16`, `endUtf16`, and `kind`. `creatorClaims.status` is always `unverified_creator_claim`. The adapter does not parse a date range or coupon code into a verified offer, follow any video-description URLs, resolve affiliate redirects, retrieve captions, or read comments.

Downstream records should keep creator statements and merchant offers as separate evidence. A creator video can establish that the creator said a product was a collaboration or advertised a particular price at publication time. Only a retailer/brand source can establish the current official offer, eligible product/variant, terms and active dates. Preserve the raw public source URL and timestamps, avoid attribution-generating link requests, and never turn a creator's claim into a current retailer price by inference.

For Data API metadata, Google requires stored API data to be refreshed or deleted after 30 days. The ontology or cache that stores descriptions must apply that refresh/delete boundary and retain the source observation time. Do not extract or store contact details from video descriptions for this promotion use case. See [YouTube API Services Developer Policies](https://developers.google.com/youtube/terms/developer-policies).
