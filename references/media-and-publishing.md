# 미디어와 발행: 요청 성공 이후의 단계

이 문서는 패키지에 포함한 과거 구현의 교훈입니다. 새로운 계정/블로그의 현재 업로드 계약을 대신하지 않습니다.

## 필요한 연결

`원본 출처 → 다운로드 바이트 → 업로드 계약 → 반환된 미디어 식별자 → 문서/HTML 삽입 → 소유자 readback → 공개 readback → 재생/렌더링`

각 단계마다 결과를 따로 남깁니다. 이미지가 업로드됐어도 문서가 예전 URL을 참조하면 반영된 것이 아닙니다. 영상 첨부카드가 보여도 인라인 재생이 된 것은 아닙니다.

### 네이버

- `service-packs/naver/apps/naver-blog-api/scripts`와 해당 README의 upload-image/upload-video/reconcile-video 흐름을 사용합니다.
- API 응답의 성공과 SmartEditor 문서에 삽입된 component의 정합성을 함께 확인합니다.
- 로그인 토큰 발급과 신규 발행 fresh SDK 입력은 다른 경계입니다. 발행기 자체가 HTTP여도 필요한 입력 준비가 엔진을 사용하면 전체 작업은 `headless_assisted_http`입니다.
- 캡션으로 표현할 내용은 미디어의 캡션 필드에 둡니다. 본문을 같은 설명으로 반복 채우지 않습니다. 최종 문서/공개 readback에서 캡션도 확인합니다.

### 티스토리

순수 문서 변환 함수와 사용법도 [Tistory recipes](../service-packs/tistory/recipes/README.md)에 포함했습니다. 제목·표·목록·링크·미디어·캡션을 옮기며 네트워크 요청은 하지 않습니다.

- 기존 관측의 핵심은 업로드 허용 origin·세션 전달·반환 계약입니다. 미디어 최종 URL의 서명 query나 세션은 Git 영수증에 넣지 않습니다.
- 과거 네이버 이미지 URL은 티스토리 referer에서 403을 반환했습니다. 그런 원문 주소를 HTML에 붙이는 것만으로 이식 완료라고 부르지 않습니다. 권한 있는 원본 바이트를 받아 티스토리 업로드 계약으로 올려야 합니다.
- 이 스냅샷에서는 네이티브 동영상 업로드 경로의 부재와 **MP4 일반 첨부**를 구분합니다. 파일 첨부 가능이 곧 네이티브 플레이어 기능 구현은 아닙니다.
- HTML5 `<video>`로 연결한 경우에도 공개 페이지의 player 속성, 실제 바이트, 응답 MIME/range, 인라인 재생 결과를 따로 확인합니다. 관련 구현/사용법은 `service-packs/tistory`에 있습니다.
- 기존 글 수정은 관측된 수정 method를 사용합니다. 이미지·영상 자리를 원문 링크로 대체해 놓았던 임시 변환 결과는 미디어 이식 완료로 계산하지 않습니다.

## 다운로드 검증

HTTP status뿐 아니라 MIME, 크기, magic bytes, 예상 포맷을 확인합니다. PNG/JPEG/GIF/WebP/MP4와 HTML 로그인 화면을 구분합니다. OOXML은 ZIP magic과 내부 구조까지 확인합니다. 같은 파일인지 비교하려면 인증값이 아닌 **파일 바이트**의 SHA-256을 사용합니다.

## 발행 판단과 전송 분리

콘텐츠 품질·출처·사용자의 게시 지시를 판단하는 단계와 HTTP 전송 클라이언트를 분리합니다. JEV 등 판단기는 인증 공급자도 사실 확인자도 아닙니다. 품질 도구 장애를 로그인 문제로 바꾸거나, HTTP 성공을 품질 검토 완료로 바꾸지 않습니다. 현재 작업에서 이미 허용된 게시 지시는 유지하고, 실제 서비스 요구와 미확인 단계만 분명히 보고합니다.
