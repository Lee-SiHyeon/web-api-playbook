# Google Flow: session propagation and the generation boundary

Checked 2026-10-05 on the owner's Windows runner. The maintained consumer client is in affiliate-content-operations/apps/google-flow-api. These observations use the Flow web project and existing web credits; they are not Gemini Developer API or Vertex AI evidence.

## Login visible in Chrome, HTTP redirected to Google sign-in

A narrow 16-name Google cookie capture omitted the host-only Flow cookies OSID and __Secure-OSID. A direct GET of the observed /project/{projectId} returned HTTP 302 to accounts.google.com/ServiceLogin. The normal browser document returned 200 and contained SNlM0e, FdrFJe and cfb2h.

The browser actually sent 21 scoped cookies, including those two Flow host cookies. After an encrypted first-party handoff into Windows DPAPI, a separate Node process parsed all three document fields and replayed protected project RPC Zzl0ze, returning 35 media records. This establishes current session propagation and that read operation. It does not establish independent password login or expired-session recovery.

Preserve the cookie array's domain, hostOnly, path, secure, session and expiry metadata. Do not use a fixed Google authentication-name allowlist that drops service-host cookies. Reject out-of-scope cookies and identical scope duplicates; keep the same name at distinct valid scopes. Chrome CDP's expires:-1 with session:true is a session-cookie sentinel, not an expired persistent cookie. Never send the Flow bundle to accounts.google.com or a media CDN by following a redirect.

Record 302 as a redacted redirect class, status and MIME. Distinguish account sign-in, same-origin routing and unknown redirects; omit query values, cookies and document tokens. A 200 document missing SNlM0e is a separate parser/input failure and does not by itself establish logout.

## Current eight-second consumer generation contract

A normal Omni 1.1 Flash setup selected one 720p, eight-second, 16:9 clip. The observed create operation is:

- POST https://flow.google.com/_/AiSandboxAngularFrontend/data/batchexecute
- rpcids: YhhmEf; URL-encoded form keys f.req and at
- Model key abra_t2v_8s; aspect value 2; project context and per-job client identifiers
- A fresh first-party reCAPTCHA Enterprise SDK input in the generation context

The observed consumer setup offers 360p or 720p. A 480p artifact requires a separately verified local conversion of a completed native clip.

Google documents the normal website execute() token flow and one-use, two-minute tokens in [Create assessments for websites](https://docs.cloud.google.com/recaptcha/docs/create-assessment-website). An assessment endpoint consumes that token; it is not a replacement issuer. No verified pure-HTTP issuer was found for Flow. Do not replay internal challenge requests, fabricate a token, substitute another service's key, or treat the SDK capture as engine-free generation.

A direct HTTP trace of the three observed public preloads (`_b`, `wO1vlb`, `XRV0Af`) located the real producer in lazy module `wO1vlb`: `_.JS.An("VIDEO_GENERATION")` waits for `enterprise.execute()`, and `q7a` serializes the result through `k5a/YhhmEf`. No separate ordinary HTTP issuer was found in those assets and the reviewed official references. This bounded trace does not establish that every private internal path is absent. The sanitized source receipt is `discovery/http-issuer-source-trace-2026-10-05.json` in the maintained app.

Further read-only branch tracing found that the execute wrapper flag changes action handling rather than selecting an HTTP issuer. The current owner document has the configured key (boolean only was recorded), so the absent-key branch is inactive. Text, reference, frame, edit, extend and upsample callers share the SDK result. That earlier read-only trace did not itself send an omission probe; the later, separately authorized missing-input diagnostic is recorded below. The observed experimental descriptor IJhj9c is registry evidence without a captured callable request. Google documents [API/IoT Express keys](https://docs.cloud.google.com/recaptcha/docs/keys), but that separate service-owned key type is not evidenced as a substitute for Flow’s web action token.

Two lazy asset URLs in the initial source receipt contained a manually transcribed extra character. Parse the current protected document’s exact public preload hrefs rather than rebuilding or copying minified paths. After correction, all three modules replayed as HTTP 200 JavaScript with SHA-256 recorded. Preserve correction history; a malformed evidence URL is not a frontend build change.

The maintained HTTP generation writer and memory-only provider interface require a pure-HTTP first-party issuer, the `VIDEO_GENERATION` action, a fresh one-time issuance window, and matching project/prompt/options/client identifiers. No pure-HTTP issuer is configured or live-verified, so the normal HTTP CLI still exits with `FLOW_HTTP_CAPTCHA_ISSUER_UNAVAILABLE` before intent, POST, or file creation. A provider declaration alone is not evidence that issuance works. Project reservation and intent are atomic; ambiguous responses retain the fence until independent owner reads reconcile that same job. A later SDK-assisted Node HTTP create succeeded with an input issued by the normal Flow web SDK; that proves the HTTP transport can submit an accepted request in that setup, but it does not provide a pure-HTTP input issuer. An unrelated local MP4 must not unlock an unknown generation.

Pure-HTTP generation remains unverified. Keep `captured`, `client_exists`, and `live_replay` separate. The later SDK-assisted Node HTTP create proves that Node can submit a request carrying a fresh input captured from the web SDK; it does not prove Node can acquire that input through HTTP. The earlier input-omitted denial and this success also do not isolate the input value from every other request-context difference.

### SDK-assisted Node HTTP create and media readback (2026-10-05)

For a separate bounded diagnostic, the normal Flow page selected the same Omni 1.1 Flash, one 720p, eight-second, 16:9 setup and obtained the `VIDEO_GENERATION` input through the web SDK. The browser's own `YhhmEf` request was canceled before send by the Fetch block; its loading-failed event was also marked canceled, with no response. The helper tab was closed before the separate Node process sent the request. At Node send time, the captured input was 8,419 ms old. The scoped Cookie multiset was verified at 21 entries; the HTTP POST and protected owner readback used the same session. The Node request did not copy browser `User-Agent` or `sec-ch-ua*` headers.

Exactly one Node HTTP `YhhmEf` POST was sent at `2026-10-05T12:23:39.546Z`. It returned HTTP 200 with a 1,462-byte JSON response containing one matching frame acknowledgement and a new media record. Protected exact-request owner readback at `12:23:55.334Z` found the matching scene and a project count change from 36 to 37. `jwpduf` showed state `3` with positive video bytes at `12:24:30.064Z`; the direct HTTP media download completed at `12:24:32.884Z` with 4,172,459 bytes. The native file is H.264/AAC, 1280×720, eight seconds, and its full decode passed. FFmpeg produced an 854×480, 24 fps, eight-second derivative of 1,598,075 bytes; its full 192-frame decode passed. `blackdetect` found zero spans at a 0.5-second minimum duration and 0.10 pixel threshold, and `freezedetect` found zero spans at −50 dB over a one-second minimum. The sanitized [SDK-assisted Node HTTP create receipt](../verification/google-flow-sdk-input-http-create-2026-10-05.json) records these checks.

This experiment demonstrates that the Node HTTP transport can create and retrieve a Flow video when given a fresh input obtained from the normal web SDK. It does not demonstrate a pure-HTTP issuer or an HTTP-only generation workflow, and it does not isolate why the earlier input-omitted requests were rejected. The standard CLI therefore remains fail-closed when no verified pure-HTTP input issuer is configured.

## Safe action capture

For an unapproved discovery write, install a fail-closed block for the exact write and associated save paths. For an explicitly authorized, bounded real create, prepare the journal and network cursor first, allow exactly one send, and reconcile that same request before any retry. Pair the attempted request with its response by requestId. Clear unused inputs and restore/close the task-owned debugger afterward. A failed UI tile caused by an intentional block is not a server rejection.

Decode field names only after verifying the operation and content type. In particular, reCAPTCHA reload/clear requests can carry binary/protobuf data. Applying URLSearchParams to such a body can expose an opaque credential as a supposed field name. Record only method, normalized path, MIME and status for those requests; never persist or output the body, token value or token fingerprint.

A later read-only comparison captured a normal Flow UI request and canceled it before the create request was sent. The comparison's generation POST count was zero. Its normalized business payload matched the maintained HTTP request builder after replacing per-request UUIDs and the one-time input with markers. The browser sent User-Agent and `sec-ch-ua*` headers that the HTTP client omitted; those browser identity headers are not copied or fabricated. The captured SDK Referer was the Flow origin root, which is now the direct client Referer. These observations validate request-shape parity, not the missing input issuer or a successful HTTP create.

The first header comparison saw 21 cookies on the paused browser request and 19 in the HTTP request; two RTS names were absent. After a fresh protected handoff, the store contained 21 scoped entries, but the two RTS cookies had expired and were correctly excluded from the outgoing request. A protected project read returned HTTP 200 and 36 media records. Cookie-count differences do not identify the cause of the earlier broad unusual-activity denial. The client accepts new cookie names only from observed `Set-Cookie` headers on the Flow origin after validating the domain, path, expiry and security attributes. It only marks reauthentication when a matching scoped authentication cookie is actually deleted. The legacy flat cookie-header format has no scope metadata: it rotates an existing name only for an observed root-path cookie on an allowed Flow/Google domain, and cannot append a name or apply a non-root path update.

The 09:08 input-omitted probe's reconciliation is recorded above; its broad error does not prove that omitting the SDK input was the sole cause, and the standard pure-HTTP create path still lacks a verified input issuer.

For an already completed media record, the HTTP client polls `jwpduf` for that exact media ID and waits for the observed state `3` with positive video bytes before asking `as29s` for the download link. A read-only parity run observed that sequence and HTTP 200 from `as29s`; that parity run made zero creates and zero downloads. The successful SDK-assisted run above separately verified one create, exact owner readback, completion and download. State `3` is documented as the completed shape observed for this media, not a complete server-state enumeration. The consultations did not verify that a missing input, a cookie difference, a Referer, or browser-only headers were the sole cause of the broad create denial. The normal web SDK producer is observed; an ordinary HTTP issuer is not. That is a current implementation blocker, not proof that no unobserved private path exists. The offline omission check shows the probe removed the final context element and changed the array length from 11 to 10. It therefore does not isolate only the input value.

The same-document `at`/`f.sid` check passed for five protected read RPCs, all HTTP 200, with one document sequence; project reads returned 36 media and credits were 1,038 at that time. The verifier ran while the 09:08 diagnostic was held, so its `FLOW_GENERATION_UNRESOLVED` guard result is historical; that job has since been manually reconciled. The check validates document provenance for those reads only. A separate local form round trip preserved Unicode, newlines and reserved characters and confirmed the exact 11-to-10 omission delta; it made no network request and says nothing about write acceptance.

The historical 228-byte error body was not retained. Its exact frame tuple, message, domain, metadata and typed `ErrorInfo` schema are unknown. Do not infer the `entry[5]` layout or assert that the numeric value 7 is a canonical gRPC status from the prior parser label alone. Current parser diagnostics treat an `ErrorInfo` reason as a candidate with `errorInfoSchemaVerified:false`; they do not promote it to an authoritative server code or record metadata values. Duplicate target RPC frames are ambiguous. Synthetic fixtures verify parser boundaries, not the lost live body.

For generation, the HTTP transport wraps a parsed RPC error as an ambiguous result and the client keeps that job `needs_reconciliation` with its project fence until independent evidence resolves the same request. Parser output alone does not establish the remote write effect or authorize releasing a fence; RPC errors do not trigger automatic release. The last recorded Flow regression run passed 89/89, including synthetic parser fixtures, before the separate SDK-assisted create documented above.
