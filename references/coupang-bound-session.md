# Coupang Partners bound service session

The Partners client uses the ordinary `AFATK` login cookie as `x-token` on business API requests. This was observed in native Chrome and in the first-party [request interceptor](https://partners.coupang.com/static/js/main.aefc650b.js) on 2026-10-03. Direct HTTP `/api/v1/config` returned HTML Access Denied while authenticated `/api/v1/dashboard` and `/api/v1/search` returned JSON success; config failure does not establish failure of every business route.

`createCoupangAuth().importAttestedSession(input)` creates a protected version 2 record only after a trusted local operator captures the successful native config request, its actual outgoing authentication cookies, and the matching owner response. It requires an existing protected owner identity. The captured config identity must match that record and all 13 ordinary authentication-cookie values must match the final scoped HTTP session. The HTTP dashboard must then succeed with the expected schema before DPAPI storage.

The proof object is trusted operator input; it is not a cryptographic browser-origin attestation. Encryption protects the handoff payload, and a random protected HMAC key binds the stored owner to the authentication-cookie identity and scope. Neither mechanism independently proves a caller-supplied proof came from Chrome. Do not expose this import as an untrusted public endpoint.

Version 2 permits only `https://partners.coupang.com`. Subsequent health/ensure/dashboard requests verify the protected binding and current HTTP dashboard authentication. They report `ownerVerificationSource: authorized_browser_config_session_binding` and `freshHttpIdentityRead: false`; dashboard success is authentication evidence, not a fresh identity query. Missing binding, owner mismatch, authentication-cookie value/scope/security changes, or rejected service authentication block use. Reauthentication remains an observed first-party bootstrap.

The binding covers cookie name/value/domain/path/hostOnly/secure/httpOnly/sameSite. Lifetime metadata is excluded because observed successful dashboard responses refreshed `Expires`/`Max-Age` for unchanged `member_srl`, `sid`, and `ILOGIN` values. Expired cookies still cannot authenticate. The four observed AWS load-balancer cookies can rotate; authentication-cookie value rotation requires another owner bootstrap. Unknown response cookie names, including challenge cookies, are filtered before jar ingestion and protected persistence.

The fetch wrapper derives `x-token` from the actual outgoing Cookie header for Partners `/api/v1/*` business routes, excluding config/prelogin; caller-supplied `x-token` and `x-de-token` are removed. No challenge material or browser fingerprint emulation is used. Version 1 retains its existing config-based owner check. Version 2 does not request an account edit/profile endpoint.

Focused verification: `node --test tests/coupang-attested-session.test.mjs tests/coupang-auth-access-denied.test.mjs tests/coupang-response.test.mjs` passed 17 tests. A live protected import and a separate-process HTTP dashboard/search replay passed on 2026-10-03. This note does not establish link destination/readback verification or public shopping-page coverage.
